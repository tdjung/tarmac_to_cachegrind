# 커버·미커버 이벤트 추가 전후 생성 시간

기준: 운영 변환기 `702add2`의 코드. 두 버전 모두 `--workers 4`로 실행했습니다.
Python 3.6.8 호환성 빌드(`CFLAGS=-O0`)에서 각 조건을 3회 측정하고 실행 순서를
교대로 바꿨습니다. 표는 중앙값입니다. 인터프리터 빌드와 장비 부하가 사용자 환경과
다르므로 실제 450개 대형 로그의 완료 시간을 예측하는 수치가 아닙니다.

| 입력 | 변경 전 | 변경 후 | 증가 | 증가율 |
|---|---:|---:|---:|---:|
| 450개 짧은 로그, 총 135,000줄 | 0.776초 | 0.924초 | +0.147초 | +19.0% |
| 12개 로그, 총 7,200,000줄 | 4.833초 | 5.013초 | +0.179초 | +3.7% |

전체 프로세스 실행 시간을 측정했습니다. ELF 분석, 로그 파싱, 개별 파일 쓰기, merge,
신규 이벤트 생성 및 목록/보고서 쓰기를 포함하며 입력 생성과 결과 비교는 제외합니다.
첫 번째 조건은 ELF 200개 함수와 로그당 100개 명령어, 두 번째는 ELF 4,000개 함수와
로그당 200,000개 명령어입니다. ES/IT 형식을 섞었고, 로그별로 실행 함수 구간을 옮겨
테스트 집합이 달라지도록 했습니다. 활성 PC 풀은 최대 256개이고 파일당 최대 절반을
실행하므로, 매우 많은 고유 PC가 실행되는 실제 펌웨어의 비용을 대표하지 않습니다.

개별 결과와 total에서 PC·소스·Ir 정보를 추출해 SHA-256을 비교했습니다.
첫 조건은 451개, 두 번째는 13개의 프로파일이 변경 전후 일치했습니다.
전체 파일 바이트는 새로운 이벤트와 이름이 추가되어 다릅니다.

내부적으로 sparse PC별 테스트 비트를 합산하고, 마지막에 소스 라인별 합집합 및
미커버 집합을 생성합니다. 추가 처리는 전체 실행 명령어 수보다는 파일마다 실행한
고유 PC 수, ELF 위치 수, 서로 다른 테스트 집합 수와 목록 크기에 영향을 받습니다.
짧은 로그 조건에서는 고정적인 최종 출력 비용의 비중이 커서 증가율이 더 컸습니다.

## 재현

```bash
git show 702add2:tarmac_to_cachegrind.py > /tmp/tarmac_before_coverage.py
python3 tests/benchmark_coverage.py --baseline /tmp/tarmac_before_coverage.py \
  --logs 450 --instructions 100 --functions 200 --workers 4 --rounds 3 \
  --report coverage_450.json
python3 tests/benchmark_coverage.py --baseline /tmp/tarmac_before_coverage.py \
  --workers 4 --rounds 3 --report coverage_large.json
```

GCC와 호스트 binutils로 실제 디버그 ELF를 생성해 합성 Tarmac 주소에 연결합니다.
표준 라이브러리만 사용합니다. 원시 측정 결과는 `coverage_benchmark_450.json`과
`coverage_benchmark_large.json`입니다. 원본 및 결과 임시 폴더는 종료 시 제거합니다.

테스트 PC 집합과 사용자 뷰어의 라인 합산 방식은 별개 검증입니다. 출력의 라인 집합과
인덱스는 자동 검사했지만 실제 사용자 뷰어의 색상과 집계 표시까지 검증한 것은 아닙니다.
