# 문자열 직접 파싱 비교 실험

기준 운영 코드: `64cac59`. 운영 `tarmac_to_cachegrind.py`는 변경하지 않았습니다.

## 방법

- 각 입력은 이벤트 후보 100,000줄 + 레지스터/메모리 200,000줄, 총 300,000줄입니다.
- 입력 생성과 검증은 측정에서 제외합니다. 메모리상의 문자열 목록을 파싱하는 시간만
  측정하며, ELF 분석·디스크 읽기/쓰기·병렬화·merge는 포함하지 않습니다.
- 각 방식을 5회 실행하고 실행 순서를 순환했습니다. 아래 값은 중앙값(초)입니다.
- 반복 입력은 256개 PC를 순환합니다. 큰 working set은 16,384개 PC를 순환하므로
  8,192개 캐시보다 큽니다. IT metadata 변경 입력은 metadata가 매 이벤트 달라집니다.
- 혼합 입력에는 ES EXC, IS, IF, CCFAIL, fetch 실패 및 malformed 기록이 포함됩니다.
  이 비교에서만 `skip_malformed=True`로 전체 통계를 확인합니다.
- 일반 ES/IT 형식은 문자열 `split`/`partition`/비교로 처리합니다. EXC, CCFAIL,
  실패한 opcode, 지원하던 변형 및 애매한 형식은 기존 정규식 검사로 fallback합니다.
  따라서 '직접 파싱'은 모든 문법에서 정규식을 완전히 제거했다는 뜻은 아닙니다.
- PC/opcode의 16진수 문법과 상태를 확인하므로 검사를 생략한 느슨한 추출기와의
  비교가 아닙니다. 새로운 파서는 실험용으로 운영 스크립트에서 사용하지 않습니다.

비교 방식:

1. 기존: 정규식 이벤트 분리 + 본문 해석 LRU 캐시.
2. 직접: 문자열 이벤트 분리 + 문자열 해석, 해석 캐시 없음.
3. 직접+PC: 2에 PC 문자열 → 정수 LRU 캐시 추가.
4. 직접+본문: 문자열 이벤트 분리 + 문자열 해석 결과 LRU 캐시.

모든 캐시의 상한은 8,192개이며 파일 단위입니다.

## 결과

### Python 3.6.8

| 입력 | 기존 | 직접 | 직접+PC | 직접+본문 |
|---|---:|---:|---:|---:|
| ES 반복 | 0.930 | 1.830 | 1.990 | 0.996 |
| IT 반복 | 0.954 | 1.665 | 1.656 | 0.992 |
| IT metadata 매번 변경 | 1.504 | 1.739 | 1.651 | 1.861 |
| ES 16,384 PC 순환 | 1.770 | 1.955 | 1.864 | 1.975 |
| 예외·미실행·오류 혼합 | 1.239 | 1.925 | 2.183 | 1.082 |

### Python 3.12.14

| 입력 | 기존 | 직접 | 직접+PC | 직접+본문 |
|---|---:|---:|---:|---:|
| ES 반복 | 0.154 | 0.281 | 0.270 | 0.140 |
| IT 반복 | 0.161 | 0.301 | 0.271 | 0.163 |
| IT metadata 매번 변경 | 0.303 | 0.285 | 0.271 | 0.314 |
| ES 16,384 PC 순환 | 0.353 | 0.273 | 0.304 | 0.333 |
| 예외·미실행·오류 혼합 | 0.170 | 0.288 | 0.279 | 0.149 |

3.6.8은 앞선 호환성 검사에서 사용한 **CFLAGS=-O0 빌드**입니다. 사용자 배포판의
최적화된 3.6.8과 동일한 환경이 아니며, 빌드 옵션은 상대 성능에도 영향을 줄 수 있습니다.
버전 간 절대 시간 비교나 실제 900개 로그의 완료 시간 예측에 사용할 수 없습니다.
원시 측정값은 `parser_results_py36.json`, `parser_results_py312.json`에 보관했습니다.
5회 측정 중 변동이 있으므로 작은 차이를 확정적인 개선으로 해석하지 마세요.

## 판단

이번 3.6.8 빌드에서는 일반 반복 입력에 대한 기존 본문 캐시의 효과가 컸으며,
직접 파싱으로 일괄 교체할 근거를 얻지 못했습니다. 본문 캐시를 유지한 문자열 방식은
반복 ES/IT에서 기존과 비슷했고, 혼합 입력에서만 더 짧은 중앙값을 보였습니다.
3.12에서는 IT metadata 변화 및 큰 ES working set에서 직접 파싱이 유리했으므로,
문자열 직접 처리의 효과는 입력과 인터프리터 환경에 따라 달랐습니다.

정규식 엔진의 C 실행을 Python의 여러 문자열 호출과 조건 검사로 바꾸는 것만으로는
항상 빨라지지 않습니다. 반복 입력에서는 해석 방법보다 해석 자체의 생략이 유리할 수
있습니다. 운영 파서는 유지하고, 실제 배포판의 Python 3.6.8에서도 아래 비교를 실행한
뒤 적용 여부를 판단하는 것이 적절합니다. 이 결과는 모든 가능한 직접 파서의 성능을
대표하거나 C++ 직접 파싱의 장점을 부정하는 결과는 아닙니다.

## 정확성 확인과 재현

두 인터프리터 각각에서 기존 ParserTests 10종을 후보 3개에 적용해 통과했습니다.
추가로 이벤트·timestamp·opcode·조건·malformed·format 설정 조합 1,764개를 후보마다
기존 파서와 비교했습니다. 모든 측정 입력의 PC별 횟수와 Stats 전체 값도 일치했습니다.
엄격 모드에서는 오류 메시지와 줄 번호도 비교했습니다. 실물 Arm 로그에 대한 검증을
대체하지 않으며, 실험용 파서를 운영 코드에 적용하기 전에는 전체 통합 검증이 필요합니다.

```bash
python3 tests/benchmark_parser.py --records 100000 --rounds 5 --output parser_results.json
```

표준 라이브러리만 필요하며 성능 검사는 기본 unittest 탐색에서 자동 실행되지 않습니다.
